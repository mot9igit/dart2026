Подходы при разработке стартапа

Кейс Стартап Ошибки

Данная статья не должна служить руководством к определённым действиям. Я старался расписать всё со стороны разработчика и на собственном опыте, с учётом своих ошибок в том числе. Распишу тезисно, с примерами из реальной жизни.

1. Документация — основной документ разработки

Любая задача, будь она сложная или нет, должна начинаться с формализации. В ходе описания функционала решаются вопросы, которые могут встать и после релиза. Кроме того, это позволяет трезво осмыслить спектр задач и расставить приоритеты.

В отсутствие документации нанимаемый персонал сталкивается с серьёзными последствиями:

  • персонал начинает дёргать других людей, чтобы уточнить детали, что портит атмосферу в команде;
  • КПД нового ресурса на первых парах сводится к нулю;
  • без понимания взаимосвязей разработчик может просто сломать систему.

2. Контроль выполнения задач и отчёты

Для контроля не обязательно проводить ежедневные дейли — всё должно быть видно по закрытым задачам. Когда мы только начинали проект, наши дейли доходили до 2 часов. От постоянных созвонов сильно устаёшь, а они не дают сконцентрироваться. Все основные участники проекта должны быть вовлечены в том числе в планирование.

На практике

Меня, как основного разработчика, ни разу не брали на совещание по планированию развития проекта — такого быть не должно.

3. Чёткость постановки задач — путь к успеху

«Без чёткого ТЗ и результат ХЗ». Никогда не нужно пренебрегать подробным описанием задачи, даже если что-то кажется очевидным. В моей практике задачи сводились примерно к таким фразам:

«Необходимо реализовать авторизацию пользователей!»
— какую авторизацию? С подтверждением или нет? OAUTH? JWT? А может, сначала регистрацию?

Чем подробнее раскроешь задачу, тем ближе к эталону будет её реализация. Крупные задачи необходимо декомпозировать.

Пример декомпозиции

Разбиваем задачу «авторизация» на атомарные шаги:

auth.js 
// 1. Валидация входящих данных
function validateCredentials({ email, password }) {
  if (!email || !password) {
    throw new Error('Укажите e-mail и пароль');
  }
  return { email: email.toLowerCase(), password };
}

// 2. Поиск пользователя в базе
const user = await db.findUser({ email });

// 3. Проверка пароля
const isMatch = await bcrypt.compare(password, user.hash);
if (!isMatch) throw new Error('Неверный пароль');

// 4. Выпуск токена (JWT или сессия)
const token = signToken({ id: user.id });

return { user, token };

4. Фокус на качестве, а не на скорости запуска

Этот тезис изначально ошибочный — всегда нужно ставить на качество продукта и тщательно тестировать функционал перед показом конечному пользователю. Что страдает первым от спешки? Конечно, качество реализации, а затем и доверие пользователей.

5. Тестирование функционала

Пренебрежение тестированием — второй по негативному влиянию «грех». Всегда нужно проводить несколько циклов тестирования, давать разработчикам время на покрытие кода юнит-тестами. Да, скорость упадёт, но результат будет таким, каким планировали.

6. Универсальность команды

У стартапов ограниченные ресурсы, но и на одном энтузиазме долго не уедешь. Чем больше разрастается проект, тем больше ресурсов он требует. Один человек недолго совмещает и backend, и frontend, и devops, и тимлид — помимо дополнительных обязанностей есть и свои, которые тоже требуют выполнения.

Нужна команда под свой проект?

Разберём задачи, предложим архитектуру и соберём разработку под ключ.

7. Рабочее время — это работа

Изначально нужно договориться с командой, кто в какое время доступен, и беспокоить только в это время. Я категорично против сверхурочной работы — она даёт лишь одномоментный эффект. При грамотно выстроенном процессе переработок быть не должно.

«Слушай, давай поработаешь в выходные и в будни побольше?» — это красный флаг.

8. Не менять вектор, если план утверждён

Процесс разработки не такой гибкий, как кажется. Если функционал запланирован — не нужно резко менять приоритеты. В моей практике изначальная идея разделилась на три проекта, и по итогу ни один из них так и не был закончен — команда скакала между задачами, а результат размывался.

Заключение

Надеюсь, описанные тезисы помогут избежать тех ошибок, что совершили мы. Главное — документация, тестирование, реалистичные сроки и уважение к команде. Статья будет дополняться.
